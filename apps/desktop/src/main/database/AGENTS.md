# Desktop Local Database — SQLite (libSQL) + Prisma

Rules for the desktop local store under `apps/desktop/src/main/database/`. Relocated from `apps/desktop/AGENTS.md` (FEA-3894); the parent file links here.

> ### A session's lifecycle state is `active` / `inactive` / `error`
>
> **There is no desktop-local copy of this vocabulary any more.** ISS-5592 step 2 deleted `DESKTOP_SESSION_STATUS`; `db-constants.ts` imports `SESSION_STATUS` from `@repo/api/src/types/session-status`, and `TERMINAL_STATUSES` / `TERMINAL_STATUS_SET` are built from it. Do not reintroduce a local mirror — it was the same value set declared twice, so every migration on this axis had to land in both.
>
> **Import the LIFECYCLE set, never the displayed one.** What this app may WRITE to `sessions.status` is `SESSION_STATUS` — `active`, `inactive`, `error`, and nothing else. `DISPLAYED_SESSION_STATUS` additionally carries `waiting`, `unknown`, and `stale`: read-time derivations with no desktop column, which must never be persisted into SQLite. Importing the narrow set is the convention that keeps the two vocabularies apart, but it is NOT a hard gate — do not read it as one. Every write to `sessions.status` goes through `$executeRawUnsafe`, so SQL can carry any string the caller builds, and nothing fails a build if someone declares a fresh `"waiting"` literal instead of importing. ISS-5592 step 2 removed the one producer that had done exactly that (`codex-otel-writer.ts` held its own `ACTIVE_SESSION_STATUS = "active"`) and typed `setSessionStatus`'s parameter `SessionStatus`, which narrows the main helper boundary. Beyond that boundary this stays review-owned. Awaiting-input is written as the `awaiting_input_since` TIMESTAMP (`setMainWaiting`), not as a status.
>
> A local row CAN still store a literal `waiting`. Migration `0042_iss4586_session_status_ends_with_error` collapsed only `completed`/`abandoned` and states in its own text that "active/waiting/running are unchanged", so nothing guarantees zero such rows. Those rows stay READABLE: the Status facet matches on the cloud `DISPLAYED_SESSION_STATUS.WAITING` (`../session/session-status-filter-match.ts`) and its SQL twin unions a raw `'waiting'` literal (`session-aggregate-filters.ts`, which calls it "a LEGACY PERSISTED status (kept for version-skew)"). Neither read goes through `SESSION_STATUS`. `DESKTOP_AGENT_STATUS` in `db-constants.ts` is a different axis (per-agent, not per-session) and keeps its own `waiting`, as is the cloud's `AgentSessionState`. Full rule: the "Session State" section of the root `AGENTS.md`.

> ### ⚠️ The local DB engine is SQLite (libSQL) — NOT Postgres/PGlite
>
> FEA-2038 migrated the desktop local store from **PGlite** (Postgres-in-WASM) to **SQLite via libSQL**. The runtime file is `src/main/database/sqlite.ts` (formerly `pglite.ts`); its symbols now use the `sqlite`/`Sqlite` prefix (`openSqliteAgentDatabase`, `SqliteExecutor`, …) — **the engine is SQLite.** The on-disk store is `agent-dashboard.sqlite` under Electron `userData`.
>
> **All hand-written SQL — raw reads/writes, aggregates, AND migration `.sql` files — MUST be SQLite dialect.** Postgres syntax silently passes typecheck/lint and then throws at runtime against the live store. Forbidden Postgres constructs and their SQLite replacements:
>
> | ❌ Postgres (do NOT use) | ✅ SQLite (libSQL) |
> | --- | --- |
> | `expr::int` / `expr::text` / `expr::timestamptz` casts | `CAST(expr AS INTEGER/TEXT)` or just omit; `Number()`-coerce counts in JS |
> | `ILIKE '%x%'` | `lower(col) LIKE '%x%'` (SQLite `LIKE` is already ASCII case-insensitive) |
> | `col ~ '^[0-9]{4}-...'` (regex) | `col GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]*'` |
> | `EXTRACT(EPOCH FROM (a - b)) * 1000` | `(julianday(a) - julianday(b)) * 86400000` |
> | `COUNT(*) FILTER (WHERE p)` | `SUM(CASE WHEN p THEN 1 ELSE 0 END)` (or `COUNT(*) FILTER` — libSQL supports it, but the codebase prefers the `SUM(CASE …)` idiom) |
> | `DO $$ … to_regclass(…) … $$` guards in migrations | plain `CREATE INDEX IF NOT EXISTS … ON …(…) WHERE …;` (SQLite supports `IF NOT EXISTS` + partial indexes natively) |
> | Dates: comparing `started_at::timestamptz` | compare ISO-8601 **strings** directly (the app only ever persists `toISOString()`); guard malformed values with the `GLOB` date-prefix expr |
>
> **Canonical pattern to mirror** (already SQLite-correct, verified against the live store): `buildUsageFilterClause`, `aggregateSqliteUsage`, and the `SESSION_STARTED_AT_TS_EXPR` / `SESSION_STARTED_AT_BOUNDS_EXPR` date guards in `sqlite.ts`. Before finishing any SQL change, grep your diff for `ILIKE`, `::`, `EXTRACT`, `~ '`, `to_regclass`, `DO $$`, `timestamptz` — there must be **zero** matches in new SQL.
>
> **Analytics invariant (FEA-2038):** dashboard analytics/usage/branch reads must compute **metadata-only SQL aggregates** (`COUNT`/`SUM`/`GROUP BY` over the metadata/token tables) and must **never hydrate the full session/event corpus into JS** — doing so OOMs the db-host utilityProcess (exit code 5) on a large local history. Row-loading list reads default to a 90-day window (all-time via an explicit toggle); aggregates stay all-time (cheap in SQL).
>
> **Migrations** are sequential `000N_<name>/migration.sql`, hand-authored in SQLite dialect (see `0001_init`, `0002_idx_token_events_session_created`, `0003_idx_branch_name`). Use the next unused contiguous prefix. The already-merged FEA-2030 timestamped migration is immutable and grandfathered by the manifest order; do not add more timestamp-prefixed migrations. Regenerate the gitignored manifest with `node apps/desktop/scripts/generate-migrations-manifest.mjs` after adding one. (This supersedes the timestamp-prefix guidance below.)

The local store schema is owned by `apps/desktop/prisma/schema.prisma` (independent of the cloud schema in `packages/database` by design — FEA-1736 decision 6). The generated client output `src/main/database/generated/` is gitignored; `pnpm db:generate` produces it and runs automatically inside `build`, `typecheck`, and `test`.

Schema changes are forward-only Prisma migrations applied at boot by the runtime migration runner (`src/main/database/migration/migration-runner.ts`). To change the schema: edit `prisma/schema.prisma`, hand-author the next contiguous `000N_<name>/migration.sql` in **SQLite dialect** (per the ⚠️ callout above — do NOT generate it against Postgres), regenerate the client with `pnpm db:generate`, and commit it under `prisma/migrations/`. The runner records applied migrations in a `_desktop_migrations` tracking table, applies each pending migration in its own transaction (no down-migrations), and refuses to boot on checksum drift or a downgraded app — surfaced as an Agent Monitor boot failure with DB IPC disabled, never a crash loop. A prebuild step (`scripts/generate-migrations-manifest.mjs`) embeds the migrations into the gitignored `src/main/database/migration/migrations-manifest.ts` so they survive asar packaging (mirrors `build-info.ts`).

**A migration is immutable once it merges to `main`.** Editing, deleting, or renaming a committed `migration.sql` changes its embedded checksum, so the runner refuses to boot for any store that already applied the old bytes (the exact checksum-drift refusal above). Never edit a merged migration; add a NEW forward migration instead. CI enforces this for both Prisma targets (cloud `packages/database` and desktop `apps/desktop`) via the `migration-immutability` job in `.github/workflows/pr-test.yml`, gated on the `database` and `desktop_database` path filters. A local dev store that hits a checksum-drift refusal after pulling `main` is recovered by resetting it — recipe in [`docs/runbooks/desktop-local-sqlite-recovery.md`](../../../../../docs/runbooks/desktop-local-sqlite-recovery.md). Only ever for unreleased migration churn; a released migration is permanent and must be fixed forward, never by editing it.

New desktop migration directory names must use the next contiguous `000N_` prefix in `apps/desktop/prisma/migrations/`. Do not rename the existing timestamp-prefixed FEA-2030 migration; it has a pinned manifest sort key because merged migrations are immutable. Do not insert a pending migration before an already-applied migration: changing manifest order can create a `HistoryGap` refusal on upgraded installs.

`src/main/database/migration/baseline-schema.ts` holds the FROZEN legacy DDL snapshot as of the runner cutover plus the `BASELINE_MIGRATIONS` it represents. **Do not edit it or append to `BASELINE_MIGRATIONS`** — it exists only to baseline a pre-runner install (re-assert the idempotent legacy DDL once, then record the baseline migrations as applied *without executing* them). Post-cutover schema lives only in new migrations.

The migration-refusal contract (`MigrationRefusalKind`, `DesktopMigrationError`, `userFacingMigrationRefusal`) lives in `src/main/lifecycle/migration-refusal.ts`, **deliberately outside `src/main/database/`**. Boot files (`app.ts` surfaces a refusal as an Agent Monitor boot failure) cannot statically import the database runtime — the boundary guard (`scripts/dependency-cruiser.config.cjs`) forbids any boot-graph value import into `src/main/database/**` (which transitively pulls in SQLite). Keeping the pure, DB-free contract in its own module lets the runner (producer) and the boot handler (consumer) share it without dragging the DB runtime into the boot bundle.

## Typed Prisma client

`src/main/database/prisma-client.ts` (`createDesktopPrisma`) builds the desktop store's ONLY access layer over the libSQL `config`, created inside `openSqliteAgentDatabase` and exposed as `agentDatabase.prisma`. It owns the connection topology: ONE **writer** `PrismaClient` plus a small pool of `query_only` **reader** `PrismaClient`s (default 2, `connection-pragmas.ts` is the single source of truth for the WAL/busy-timeout/cache PRAGMAs every connection applies). Three verbs, no second layer to choose between:
> - **`prisma.write(fn)`** — all writes + `$transaction`, serialized through the shared write queue on the writer connection. A throttled `wal_checkpoint(TRUNCATE)` fires after each write to bound WAL/RSS during the backfill.
> - **`prisma.read(fn)`** — heavy/independent reads that must run CONCURRENTLY with the first-launch backfill writer (sync hydration, analytics/usage aggregation, cursor paging). Dispatched round-robin to a reader connection; each reader self-serializes its own statements via the adapter's per-connection `async-mutex` (the SIGTRAP guard — one connection never runs two statements at once), and separate readers run in parallel over the WAL snapshot. `fn` gets a read-only client with a read-scoped `$transaction` for multi-read snapshots.
> - **`prisma.client`** — light reads co-located with writes (read-your-writes) on the PRIMARY/writer connection.
>
> `prisma.client` and the `prisma.read` client are both typed as a **read-only facade** (`DesktopPrismaReader`) — calling a mutation method is a compile error, so the write-queue rule is type-enforced, not convention; `query_only=ON` backstops the reader pool at the engine (a write faults with SQLITE_READONLY). The community adapter is exact-version-pinned and confined to this one module so a swap to the FEA-1736 in-house `SqlDriverAdapter` fallback touches one file — **production code must not import the adapter anywhere else**. The sole exception is the characterization test (`test/prisma-sqlite-adapter.test.ts`), which imports the adapter directly on purpose to exercise the raw client↔adapter contract against the real schema; all other tests go through the factory (`test/prisma-test-utils.ts`).

There is ONE client — no separate raw `storeDb` handle. Queries that don't map cleanly to a typed delegate run on the same `DesktopPrisma` client via Prisma's raw escape hatch (`$queryRawUnsafe` for reads, `$executeRawUnsafe` for writes). The community adapter implements `queryRaw`/`executeRaw`, so raw SQL works through it (characterized in `test/prisma-sqlite-adapter.test.ts`: `$queryRaw`/`$transaction` and the `$queryRawUnsafe`/`$executeRawUnsafe` positional-param variants the write path uses). Raw **writes** are reachable only inside `prisma.write(...)` (the full client); raw **reads** outside a write use `$queryRaw`/`$queryRawUnsafe`, which the `DesktopPrismaReader` facade re-exposes read-only (`$executeRaw*`/`$transaction`/typed mutations stay compile-errors on the facade). The read-vs-write split on `$queryRaw*` is by convention — SQL can't be statically classified — so never smuggle a mutation through it; raw writes go through `prisma.write`.

**Typed-first is the default.** Every store runs on the single `DesktopPrisma` client: typed delegates where the query has a clean form, and the raw `$queryRawUnsafe`/`$executeRawUnsafe` escape hatch (on the same client) only for SQL with no clean typed form — aggregations and window/recursive-CTE queries, group-bys over a joined relation's columns, `@@ignore`'d tables (e.g. `token_events`, which has no PK and so no generated delegate), and hand-tuned `INSERT … ON CONFLICT DO UPDATE` upserts whose COALESCE/CASE merge logic Prisma's `upsert` can't express. The raw hatch is for un-typeable SQL, NOT a shortcut. One nuance worth keeping: a single server-side aggregate-join (e.g. the session-detail `COUNT(agents)`/`COUNT(events)`/`SUM(tokens)` fold) stays raw on purpose — replacing it with per-table `groupBy` reads marshalled into a JS join is a real performance regression, so performance is a valid reason to keep raw SQL. INTEGER/`BIGINT` columns that a raw read can surface as `bigint` through the adapter are coerced to JS numbers at the existing `Number()` / `readStorageTokenCount` / `token()` boundaries (a bare `BIGINT` column surfaces as `bigint`; a `SUM`/`COUNT`/`COALESCE` expression stays `number`). **Packaging:** the `prisma-client` generator emits pure TypeScript that `tsc` compiles into `dist/` like any other module, and `@prisma/client`'s driver-adapter runtime ships no `.wasm` here — so `stage-packaging-app.mjs`'s recursive `dist/` copy carries the client with no extra asset-copy step.

Guard and store-contract tests live under `apps/desktop/test/prisma-*.test.ts` and `*-contract.test.ts` — plus `test/migration-runner.test.ts` (fresh / baseline / older-legacy / pending / rollback / drift / downgrade), `test/pack-catalog-seed.test.ts` (the catalog seed), `test/enrichment-repo-identity.test.ts`, `test/codex-otel-writer-prisma.test.ts` and `test/maintenance-write-txs.test.ts` for Electron-free write/transaction coverage. The contract tests run against a real libSQL DB and pin each store's typed-vs-raw read behavior plus bigint→number coercion; the ones that go through `openSqliteAgentDatabase` double as CI runtime gates. Shared setup lives in `test/prisma-test-utils.ts`, which reuses the production `createWriteQueue` so the test queue can't drift. CHECK constraints cannot be expressed in PSL and are hand-carried in migration SQL — see the comment in the `*_init` migration.

Desktop migrations are covered by the FEA-1520 lint gates (`scripts/lint/check-destructive-migrations.ts`, `scripts/lint/check-raw-sql-pk.ts`), which run once per schema target (cloud + desktop).

## DB host process boundary (FEA-2038)

SQLite + Prisma + every store run in a dedicated **DB host** `utilityProcess` (`database/db-host/`), NOT the main process. The main process holds `agentDatabase` as a **forwarding proxy** (`createDbHostAgentDatabase`) that turns each `agentDatabase.<path>(args)` call into one IPC `invoke` to the child. It works for any method whose **args and result are structured-clone-safe**: plain objects, arrays, numbers, strings, `null`. `prisma.client.*` reads work (delegate args are plain objects).

> **Never call a callback-taking method on the proxy from the main process.** `agentDatabase.prisma.read(fn)` / `agentDatabase.prisma.write(fn)` pass a **function**, which cannot be structured-cloned across the process boundary, so the call rejects with `DataCloneError: "An object could not be cloned"`. The `prisma.read`/`prisma.write` verbs exist to run a callback AGAINST the live connection, so they are only callable INSIDE the DB host, never from main through the proxy.

When main needs data or a write that internally uses `prisma.read(fn)`/`prisma.write(fn)`, do NOT reach for `agentDatabase.prisma` from main. Instead expose it as a **clone-safe op that runs in the child** and call that:
> - **A method on `SqliteAgentDatabase`** (no callback args, serializable return), e.g. `sessions.count()`, `runHistoricalBackfill(gitPath, batchSize)`, `propagateAllBranchPrLinks()`. The proxy forwards the dotted path and the real method runs its `prisma.read/write` callback locally in the child. This is the default.
> - **A `store:`-prefixed op** registered in `db-host-worker.ts` `storeOps` (e.g. `catalog.fetch.run`) for callback-taking store functions that live outside the `SqliteAgentDatabase` surface, invoked from main via `invokeStoreOp(...)`.

The proxy is deliberately loud: a missed reroute throws `DataCloneError` at the call site rather than silently returning wrong data. "An object could not be cloned" in the desktop logs means a main-process caller is passing a callback (or other non-cloneable value) through the proxy. Reroute it to a child op. Regression-guarded by `test/agent-dashboard-ipc-perf.test.ts` (the `session_count` dimension counts via the clone-safe `sessions.count()` method, never `prisma.read` from main).

> **Never call `.bind()`, `.call()`, or `.apply()` on a proxy method — `NON_OP_PROPS` in `db-host/db-host-agent-database.ts` answers all three (and `then`/`catch`/`finally`) with `undefined`.** `agentDatabase.someOp.bind(agentDatabase)` therefore throws `TypeError: agentDatabase.someOp.bind is not a function` at the call site. Before that guard existed, `<op>.bind` resolved as an op path and calling it posted the **proxy itself** to the child — not structured-clone-safe — which took the app down twice (ISS-4620, ISS-4818). A plain capture is NOT blocked and is safe here (`const read = agentDatabase.someOp; read()` still forwards `someOp`; the `apply` trap ignores `thisArg`), but prefer a closure — `read: () => reader.someOp()` — because it behaves the same whether `reader` is this proxy, a real `SqliteAgentDatabase`, or the plain-object fakes the tests pass. That is what `token-parity.ts`, `foreign-key-integrity.ts`, `invocation-telemetry-integrity.ts`, `database-integrity/store-integrity-probe.ts` and `../telemetry/import-health-telemetry.ts` all do. Pinned by `test/db-host-proxy-non-op-props.test.ts`, which asserts the detach throws locally and that **zero** op paths reach the IPC boundary. ISS-5467 proposed a repo-wide source gate on `.bind`; it was not added because this runtime guard already contains the hazard and catches aliased/dynamic access a source scan cannot see.
