## New detection pattern (2026-07-07): bearer-credential-at-rest hashing consistency
When reviewing OAuth/session/authorize flows, check that every stored bearer credential (authorization codes, refresh tokens, session tokens, one-time codes) is hashed/fingerprinted at rest, NOT plaintext. Cross-check sibling tables: this repo hashes most of them (`OAuthRefreshToken.tokenFingerprint`, `DesktopAuthorizationCode.codeHash`, `getTokenFingerprint()` sha256 in apps/mcp/src/index.ts) — a table that stores the raw credential (`OAuthAuthorizationCode.code String @unique`, queried by raw value) is an outlier worth flagging even when PKCE/short-TTL/single-use mitigate practical exploitation (defense-in-depth, usually LOW). grep: `@unique @map` on a `code`/`token`/`secret` column in schema.prisma, then confirm the store/lookup path doesn't hash first.

**REMEDIATION MUST BE AN ADDITIVE EXPAND/CONTRACT MIGRATION (learned 2026-07-12 from Codex feedback on FEA-2694/2775/2909 fix PRs).** When the credential lives on a table that `apps/mcp` (or `apps/relay`) reads/writes, the fix cannot be a one-shot destructive `RENAME`/`DROP COLUMN` (or `ADD COLUMN ... NOT NULL` on a still-populated table). Those services run on ECS (`build-mcp-server.yml`) and roll **independently** of the Vercel/`packages/database` migration path — the two are NOT atomic, so during the rollout-skew window old tasks still read/write the old plaintext column while the migration has already changed the schema. A destructive migration turns `/oauth/authorize` + `/oauth/token` into missing-column/required-field **500s** for the skew window, not just an invalidation of in-flight codes. Correct shape: EXPAND phase = keep the old column (make it NULLABLE, retain its unique index) and ADD the new hashed column NULLABLE + unique; new-image app code writes/reads only the hashed column, old image keeps working on the old column (Postgres unique indexes permit multiple NULLs so both coexist); a follow-up CONTRACT migration drops the old column and enforces `NOT NULL` once every ECS task is on the new image. Reviewers reject destructive credential-column migrations here as a P1 rollout risk every time — prescribe (or, in fix mode, implement) the additive expand phase up front. Deleting in-flight rows is NOT a substitute; it does not make the schema backward-compatible.
