## Analysis Mode (no PR context)
Hunt non-idempotent and unsafe-failure paths, newest-change-first. Map the surfaces: queues/jobs/workers, webhook receivers, schedulers/crons, and outbound calls with retries. `rg -n "webhook|enqueue|queue|worker|cron|schedule|retry|backoff|processMessage|handler|consume|BullMQ|sqs|pubsub" apps packages -g '*.ts'` and `rg -n "fetch\(|axios|http|generateText|messages\.create" apps packages -g '*.ts'` for outbound calls.

1. **Non-idempotent message/job handler** — a queue/worker/webhook handler that INSERTs, appends, sends, or charges without a dedup key, so at-least-once redelivery double-applies. Look for `create`/`insert`/`send`/`.push`/increment in a consumer with no uniqueness guard on an event/message id. Remediation: dedup on a stable id (unique constraint + `onConflict`/upsert, or a processed-ids table); make the effect idempotent.
2. **Webhook without replay/signature-verified idempotency** — an inbound webhook that acts on delivery id-blind (no idempotency key, no dedup), so a provider re-delivery repeats the effect; or one that isn't signature-checked before mutating (that half → Steve). `rg -n "webhook|/hooks/|verifySignature|svix|stripe.*constructEvent" apps`. Remediation: record + short-circuit on delivery id; return 2xx only after the idempotent commit.
3. **Retry that repeats a non-idempotent side effect** — a retry/backoff wrapper around an operation with an external effect (payment, email, provider call, DB write) that isn't safe to repeat, so a transient failure after the effect double-applies. Remediation: make the wrapped op idempotent (idempotency key to the provider), or split the effect from the retryable part.
4. **Missing timeout / unbounded await** — an outbound `fetch`/SDK/provider call or a DB/queue op with no timeout/`AbortSignal`, so one hung dependency stalls a worker or request indefinitely (and its retry piles on). `rg -n "fetch\(|await .*(create|generate|invoke)" apps packages -g '*.ts'` then check for `AbortSignal.timeout`/deadline. Remediation: bound every outbound call; fail fast and let the (idempotent) retry handle it.
   - **A configurable timeout parsed from env must be guarded to `AbortSignal.timeout`'s accepted domain, not just finite-and-positive.** `AbortSignal.timeout(delay)` (and `setTimeout`) require a positive **integer** ≤ `2_147_483_647` (2^31-1): Node throws a `RangeError` on a fractional or out-of-range value and silently clamps anything above 2^31-1 to 1ms. The obvious `Number.isFinite(v) && v > 0` guard lets `MCP_..._TIMEOUT_MS=12.5` or an oversized value through, so *every* bounded call then throws before fetch starts — the timeout you added to prevent a hang becomes a total outage. Guard with `Number.isInteger(raw) && raw > 0 && raw <= 2_147_483_647`, else fall back to the default; share ONE helper across the sibling timeout consts rather than copy-pasting the IIFE (reviewers flag the duplication too). The paired test must assert the *actual delay value* reached `AbortSignal.timeout` — spy on `AbortSignal.timeout` and assert `toHaveBeenCalledWith(30_000)` for the default and for a configured override, plus fractional / oversized / negative fallback cases; asserting only `signal instanceof AbortSignal` proves the call was bounded but NOT that the configured deadline was honored. Note: `apps/mcp` tests are NOT in the required `pr-test.yml`/Dagger test lane, so a green PR check does NOT mean new mcp tests ran — validate locally with `pnpm -C apps/mcp test` before trusting green (learned from FEA-3838 #3513, human-approved by reviewer wongk 2026-07-23).
   - **A blocking wait inside `withDb.tx` needs an explicit timeout override.** `withDb.tx` (packages/database/index.ts) takes `options?: { maxWait?: number; timeout?: number }` and passes them to `db.$transaction`; with no override it inherits Prisma's **5s default interactive-transaction timeout**. Any tx whose body can *block* — `pg_advisory_xact_lock`, `SELECT ... FOR UPDATE`, a lock-ordered write, or a large batched `createMany` — will abort with a P2028 transaction timeout instead of waiting, which turns the very serialization you asked for into a 500. Whenever the remediation is a lock or the tx body is long-running, the finding must also require sizing `{ maxWait, timeout }` for the worst case (the longest concurrent holder's work, plus this tx's own). The convention in `apps/api` is named module-level constants at 30s timeout / 5s maxWait (see `backfill-projection-writer.ts`), not inline literals.
5. **Partial-failure / no atomicity** — a multi-step operation that writes A then B with no transaction or outbox, so a crash between them leaves inconsistent state (row created, event never emitted; money moved, ledger not updated). Remediation: wrap in a transaction, or use an outbox/saga so the second step is recoverable; never emit a success-shaped result before the durable commit.
6. **Success-shaped output on failure (swallowed error kills retry)** — a `catch` that logs and returns success / resolves, so the queue/caller acks and NEVER retries a real failure (and the work is silently lost). `rg -n "catch\s*\(" apps packages -g '*.ts'` and read the block for return-success/absorb patterns. Remediation: rethrow or return a typed failure the queue/caller can act on; only swallow genuinely-ignorable errors, explicitly.
7. **Ordering / concurrency hazard** — a handler that assumes in-order delivery or single-flight when the transport gives neither (two messages for the same entity race a read-modify-write; a later event overwrites an earlier one with stale data). Look for read-modify-write without optimistic concurrency (version/`updatedAt` guard) or a lock. Remediation: guard with optimistic concurrency or a per-entity lock; make the update commutative/monotonic where possible. When you recommend a lock inside `withDb.tx`, pair it with the `{ maxWait, timeout }` sizing from category 4 — a lock without the override just converts a race into a 5s Prisma timeout.
   - **Read-then-write dedupe inside a tx is NOT concurrency-safe by itself.** A common "idempotent" pattern here is: open `withDb.tx`, `findMany` the existing rows, build a Set, then `create` only the missing ones (e.g. `createPackComponents` in catalog/service.ts). `withDb.tx` (packages/database/index.ts) calls `db.$transaction` with NO `isolationLevel`, so it runs at Postgres default **READ COMMITTED** — two concurrent txns do NOT see each other's uncommitted inserts, so both create the full set → duplicates. The read-based dedupe only protects against a *committed earlier* run, never a truly concurrent one. It is safe ONLY if a DB unique constraint (or partial unique index) backs the natural key, or the tx is Serializable. When you see this pattern, check `schema.prisma` + `migrations/*/migration.sql` for a unique index on the dedupe key; if none (or a partial one covering only some rows, e.g. `WHERE target_kind='agent'`), it's a finding. A comment claiming re-runs are idempotent "including concurrent writes" is a red flag, not proof.
8. **Scheduler/cron overlap** — a cron/scheduled job with no overlap guard, so a slow run and the next tick run concurrently over the same data. (Workflow-level `concurrency` on GitHub Actions is Pipeline Pat — you own the app/job-runtime side.) Remediation: add a run-lock / skip-if-running / `concurrency` guard.

The catalog `createPackComponents` note (category 7) generalizes: whenever a service dedupes by `findFirst(X)`-then-`create` inside `withDb.tx` (READ COMMITTED, no isolationLevel), the guard is concurrency-safe ONLY if a DB unique constraint backs key X. `recordDeployment` (deployments/deployment-service.ts) dedupes on `artifact.external_url` — which has NO `@@unique` (only `@@unique([organizationId, slug])`) — so redelivered/concurrent `deployment_status` webhooks stack duplicate DEPLOYMENT artifacts. ### Detection pattern: local-first desktop sync retry against a non-idempotent cloud create (verified live 2026-07-19)
The desktop "local-first" stores queue a local row (`sync_status='local_pending'`, `cloud_comment_id`/cloud-id NULL) and a background sync loop POSTs it to the cloud, then stamps the returned cloud id on success. On ANY upload error the loop marks the row `sync_failed` and re-POSTs it next cycle. This is at-least-once by construction, so the cloud CREATE endpoint it targets MUST dedup on a client-supplied idempotency key — otherwise a POST that commits server-side but whose response is lost (timeout, or the app is killed before the "mark uploaded" write) is replayed and DOUBLE-CREATES. This was FIXED and human-confirmed (FEA-3598/3599, #3260, resolved 2026-07-21): the trace-comments cloud create/reply now carry a client-supplied `clientId` and wrap the write in `runIdempotentTraceWrite(clientId, ...)`, which catches the concurrent-duplicate P2002 (via `getPrismaErrorCode`, `apps/api/lib/db-utils.ts`) and retries once; on retry the `findUnique` short-circuit returns the existing thread/reply as the deduped outcome. The reviewer explicitly endorsed check-then-insert over a bare `upsert` here because the create mints a nested `comments.create` and the notify decision needs the new-vs-existing (`isNew`) signal an upsert can't surface — so DO NOT flag "why not just upsert" on a check-then-insert that consumes an `isNew`/`isReplay` signal. The generalized rule below still applies to OTHER local-first stores: WHEN YOU SEE a desktop store with `sync_failed`/`local_pending` retry statuses and a `mark*Uploaded`/`mark*SyncFailed` pair, TRACE the create POST it drives and confirm the cloud endpoint accepts + dedups a stable client id; if the payload carries no client id / the endpoint does a bare `.create`, it's a RETRY_DOUBLE_EFFECT finding. Web (`apps/app`) posts directly with no retry queue, so this is desktop-specific — but the missing server-side dedup is the shared root, so recommend the fix at the cloud endpoint. NOTE: these desktop cloud fetches (`fetchCloudTraceComments`) also lack an AbortSignal (secondary NO_TIMEOUT).
