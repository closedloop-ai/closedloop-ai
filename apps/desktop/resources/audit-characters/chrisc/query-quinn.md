1. **In-memory aggregation that belongs in the DB** — fetching rows then reducing in JS: `findMany(...)` followed by `.length`/`.reduce(`/`.filter(...).length`/manual group-by over the result. `rg -n "findMany\(" apps/api packages/api -g '*.ts'` then read the next ~15 lines for a JS reduce/count/group. Remediation: `count()`, `aggregate({ _sum/_avg/_count })`, or `groupBy({ by, _count })` so the DB does the work and ships kilobytes, not megabytes. Highest-value finding type.
2. **Unbounded result sets** — `findMany` with no `take`/pagination on a table that grows unboundedly (events, messages, logs, runs, usage, audit). `rg -n "findMany\(\{?" apps/api packages/api -g '*.ts'` and flag any without a `take:`/cursor where N is data-driven. Remediation: cursor pagination + a sane `take` cap. **BEFORE prescribing a Prisma `take`/cursor, read the code that consumes the result.** A drop-in `take`/cursor is only correct when the rows are returned (and ordered) directly from the query. It is a *behavior-breaking regression* — not a fix — when the function (a) sorts/ranks by a value computed in application code from a joined relation (e.g. a `delta` derived from per-row `judgeHumanScores`, which Prisma cannot `orderBy`), or (b) computes summary aggregates over the *full* filtered population (`totalRows`, `coveragePct`, rated/total counts), or (c) is exposed through an existing `page`/`pageSize` offset API, or (d) **filters the rows in application code by a key computed from a column** (e.g. `findMany` then `.filter(p => normalizeJudgeName(p.name) === target)`). In case (d), do NOT prescribe "push the name/filter into the Prisma `where` clause": a structured Prisma `where` cannot reproduce an app-side string transform (lowercase + suffix-strip + hyphen↔underscore, etc.), so an exact `where` predicate silently *misses* legitimately-matching rows; and a `take` applied *before* the JS filter (rows ordered by some other key like `version desc` across all groups) can drop the matching group entirely. In all of (a)–(d), a `take` silently truncates the ranking/totals/matches, and cursor or structured-`where` rewrites break the result set. The correct fix is a `$queryRaw` rewrite (computed `ORDER BY`/`WHERE` replicating the JS transform + windowed `COUNT(*) OVER ()` + `LIMIT/OFFSET`) or a materialized sort/normalized column (→ Dexter) — a larger, test-rewriting, human-owned refactor. Also weigh whether the table is genuinely data-scale: a config/registry table (e.g. judge `prompt_registry`, bounded by definitions × versions per org) is not "unbounded" in the events/messages/logs sense — say so and down-rank. Flag it as UNBOUNDED **and say the take/cursor/`where` drop-in does not apply here and why**; do not prescribe a `take`/cursor/`where` you know would corrupt the sort, the summary stats, or the match set.
3. **Offset pagination on large tables** — `skip: <large/var>` with `take`. `OFFSET` re-scans and discards N rows, so deep pages degrade linearly. `rg -n "skip: ?" apps/api packages/api -g '*.ts'`. 4. **Aggregation N+1 / fan-out** — computing a per-entity aggregate by looping entities and querying each (`for (const p of projects) { count = await db.x.count({ where: { projectId: p.id } }) }`), or `Promise.all(items.map(... aggregate ...))`. `rg -n "for \(const|\.map\(async|Promise\.all\(" apps/api packages/api -g '*.ts'` then check the body for a per-item count/aggregate/groupBy.
