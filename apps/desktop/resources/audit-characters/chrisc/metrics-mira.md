### A. Correctness — "are the numbers right?"
1. **Wrong/edge-case denominators** — averages, rates, and percentages that divide by a possibly-zero or filtered count (`/0 → NaN/Infinity`), or divide by the wrong population (e.g. dividing by total rows when the numerator was filtered). Read each `/` in a metric path and check the denominator's guard and population.
2. **Double counting / wrong grain** — summing a value that's already aggregated, counting a joined/`include`d row set that fan-out-duplicates parents, or mixing grains (per-event vs per-session) in one total. Check `reduce`/`_sum` over a relation that a join multiplied.
3. **Null / undefined skew** — `null`/missing values silently treated as 0 in an average (drags the mean) vs correctly excluded; `?? 0` applied before an average; empty arrays returning 0 vs "no data". Decide which is intended and flag the mismatch.
4. **Unit / timezone / rounding bugs** — ms vs s vs tokens vs cents mixed in one calc; date bucketing in local time vs UTC so day boundaries shift; `toFixed`/`Math.round` applied mid-pipeline causing accumulation error; integer division truncating. `rg -n "toFixed\(|Math\.round\(|/ 1000|/ 100|getDate\(|getHours\(|new Date\(" apps/ packages/ -g '*.ts' -g '*.tsx'`.

### SQLite bare `GROUP BY subagent_type` binds the RAW column, not the SELECT's COALESCE alias — desktop↔web drift (learned 2026-07-21, confirmed empirically)
When a desktop SQLite read SELECTs an effective key `COALESCE(NULLIF(TRIM(subagent_type),''), NULLIF(TRIM(type),''), 'unknown') AS subagent_type` but writes a **bare** `GROUP BY subagent_type`, SQLite binds that bare name to the RAW `agents.subagent_type` **table column** (not the output alias — table columns win over aliases in GROUP BY; verified with `sqlite3 :memory:`). So every null/empty-`subagent_type` row collapses into ONE bucket regardless of differing `type`; the label becomes an arbitrary group member's type (or a `MAX(type)` crutch) while COUNT/SUM(success/error)/COUNT(DISTINCT session)/avg_duration/edge-weight span the mixed set. The **web/cloud twin is CORRECT** because there `subagent_type` is only a JSONB-derived alias (`elem ->> 'subagentType'`) with NO table column by that name, so its identical `GROUP BY subagent_type` binds to the COALESCE — same data, different "Agents by type" breakdown on desktop vs web. **Tell:** a SELECT alias whose NAME collides with a real table column + a bare `GROUP BY <that name>` (or `GROUP BY <qualified raw col>` in the edge self-joins), especially alongside a `MAX(type)` label crutch. The SAME file's edge query naming its aliases `source`/`target` (no column collision) groups correctly — proving the collision is the trap. Confirmed 2026-07-21 buggy: `local-insights.ts:295` (Insights agent-pipeline nodes, twin of correct `apps/api/app/insights/service.ts:1014`), `dashboard-queries.ts:409/414,433/437,734/742` (coaching subagentTypes/edges/getSubAgents). The already-correct in-repo template is `sync-source.ts:1515` `GROUP BY COALESCE(a.subagent_type, a.type, 'unknown')`. Rule: for any SQLite aggregate, whenever a SELECT aliases a COALESCE/NULLIF expression to a name that ALSO exists as a table column, verify the GROUP BY repeats the full expression (or uses a non-colliding alias) — never a bare column name. Signature family `subagent-type-groupby-raw-column-null-collapse:<file>:<query>`. ### Normalized-slug overwrite undercount (learned 2026-07-12, FEA-2923): SQL GROUP BY raw key + JS `Map.set()` on a normalized slug silently drops rows
When a desktop reader builds a usage/metric map keyed by a NORMALIZED identity (`orgIdentitySlug` lowercases+trims `component_key`, folds null→"") but the backing SQL `GROUP BY`s the RAW column, two DB groups differing only in casing/whitespace/null-vs-empty collapse to one slug — and a `bySlug.set(slug, …)` (overwrite, not `+=`) keeps only the LAST group, undercounting invocations/sessions. Desktop keys are stored un-normalized (read paths do `lower(trim(COALESCE(component_key, name, '')))`), so collisions are structural, not hypothetical. The cloud producer for the same identity accumulates (`aggregateUsageIntoMerged` uses `+=`), so this is also a desktop↔web undercount. Grep desktop readers for `.set(` on a slug/normalized key whose source SQL groups by the raw column; fix by accumulating into the existing entry or `GROUP BY lower(trim(...))`. Confirmed 2026-07-12 at `shared-agent-components-api.ts:242` `usageBySlug`. Signature `usage-overwrite-not-accumulate:<file>:<fn>`.
  - **But for `COUNT(DISTINCT session_id)`-style aggregates, JS `+=` is ALSO wrong — it DOUBLE-COUNTS (learned 2026-07-13, FEA-2998 fix review).** Once you switch the overwrite to accumulate, summing per-raw-key `COUNT(DISTINCT session_id)` across colliding variants counts a session that logged usage under two variants once PER variant. A distinct-count union cannot be reconstructed by summing after the fact — do the union in SQL: `GROUP BY component_kind, lower(trim(COALESCE(component_key,'')))` so the distinct count spans the whole normalized identity. `SUM(invocations)` stays additive (summing IS correct there); only the distinct-session count needs the SQL-level union. Mirrors the cloud producer, which unions session ids per identity via a `Set`. Multiple reviewers + a human flagged the session double-count on the naive accumulate fix — prefer the SQL-normalized GROUP BY, not JS `+=`, for distinct counts.
  - **Normalize the identity key in EVERY read path — list AND detail (learned 2026-07-13, FEA-2998).** A list endpoint that normalizes the key (`lower(trim(...))`) while the sibling detail/single-identity endpoint filters on the RAW `component_key` makes the two disagree for the same slug (detail sees only one variant's rows and reads a different count than the list). When you fix a list aggregate's key normalization, grep for the detail/`getDetail`/single-identity query for the same table and apply the SAME normalization to its `WHERE` and `GROUP BY` (pass the already-normalized slug key). Signature `list-detail-key-normalization-drift:<file>:<fn>`.

### Calibration (learned): separate a *correctness bug* from a *defensible choice* before recommending a fix
Fix Mode auto-applies your remediations, so only true correctness bugs — a metric that yields a *wrong value for a definably-correct answer* — should be written as fixes. Several drift items above are **NOT** auto-applyable fixes; raise them as **flagged-for-human-decision opportunities** with the caveat, not as a calc to change overnight:
- **Population vs sample std dev (÷N vs ÷N−1) is a defensible *choice*, not a bug.** Switching to N−1 (a) **divides by zero at N≤1** (→ NaN/Infinity, a real regression the current ÷N avoids) and (b) shifts *every* previously-calibrated variance/CI/threshold output. ### Don't hand-roll a helper your own fix could reuse (learned 2026-07-16, FEA-2949/FEA-2944 fix reviews)
Reviewers flagged the SAME class on two fix PRs the same night: the fix introduced a *new* local implementation of logic that already existed one screen away. - **FEA-2949**: a new median filter inlined `row.additions != null && row.deletions != null` while the file's own `isLocEnrichedRow(row)` predicate was already used by `locRows` twenty lines below. Call the predicate.

### Partial-window rollout: a lookback/date selector added to SOME facets must reach EVERY metric rendered under its label (learned 2026-07-22, FEA-3722)
When a PR threads a rolling-window/date selector (7d/30d/90d/All) into a producer, it commonly windows only the facets that feature touched and leaves sibling metrics all-time — but they end up rendered under the SAME window label, so the UI/LLM asserts all-time numbers as within-window. Confirmed 2026-07-22: FEA-3722 windowed the desktop Coding Wrap's tokens + toolUsage (`getTokenAnalytics`/`toolWindow`) but left `getAnalytics` `totalSessions`=`session.count()` and `totalEvents`=`event.count()` (`dashboard-queries.ts:352,354`) unwindowed, plus `avgSessionDurationSec` from a DIFFERENT producer (`getWorkflowData` AVG-over-all-sessions, `:567`) — and `agent-coaching-llm.ts:178-183` labels the whole block "Lookback metrics (last N days)". Net: selecting 7d feeds the coaching LLM all-time counts framed as within-window. Rule: when auditing any window/date-selector PR, enumerate EVERY metric shown under the window label (walk the consumer's prompt/render block, not just the producer's diff) and confirm each honors the window — bare `.count()`/`COUNT(*)` with no WHERE, and cross-producer stats pulled from an UNwindowed sibling (`getWorkflowData`), are the usual stragglers. Signature family `lookback-window-mismatch:<producer-file>:<fn>`. Auto-applyable when the window field is unambiguous (window the count by the same cutoff the token facet uses).
  - **Fix-implementation note (learned 2026-07-23, FEA-3837 review): relabeling only the OBVIOUS unwindowed metrics is an INCOMPLETE fix — classify EVERY metric under the label into one of THREE scopes, not two.** FEA-3837 moved sessions/events/avg-duration out of the "last N days" block but left shell-ratio/repeats/frustration/plan-mode/prompts/cadence AND `totalSkillInvocations` framed as windowed; the human reviewer flagged the remaining holes and the fix had to reframe them too. The trap: those stragglers derive from `recentEvents` = the latest ≤200 rows via `getEventFeed` (NO date cutoff) and `getAllSkills` (all-time) — **a fixed-N "latest rows" feed is a recency-capped SAMPLE, not a time window, and is just as mis-labeled by a "last N days" header as an all-time `COUNT`/`AVG`.** So a source honors the window ONLY if its own query applies the date cutoff; everything else is either lifetime-all-time or recent-sample and must be labeled by its real scope. Two more traps the same review surfaced: (a) **the label-CONSTRUCTION path may not thread the range even when the return-value path does** — `buildAgentCoachingLlmRequest` called `summarizeLookback(input)` with no range, so an all-time ("All") load fell back to the 30-day default label while `loadTips`'s own `groundedMetrics` threaded it correctly; verify EVERY construction site that renders the window label passes the selected range (and that the sentinel — here `null`/`windowDays 0` — renders "all time", not "last 0 days"). (b) **a `??` fallback can silently switch a metric's scope under a fixed label** — `eventsAnalyzed: analytics?.totalEvents ?? recentEvents.length` degrades from an all-time count to the capped sample when analytics is absent, so a value labeled "all time" becomes a sample; carry a provenance flag and label the fallback honestly rather than asserting the primary scope (and do NOT change the metric's VALUE if a null-safe activity gate reads it — flag-and-relabel, don't renull). Signature stays `lookback-window-mismatch:<producer-file>:<fn>`.
