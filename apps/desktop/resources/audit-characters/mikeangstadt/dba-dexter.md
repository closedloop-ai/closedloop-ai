**Serialization-fix conventions (from PR #2718 review, 2026-07-13):** when your fix serializes a check-then-act with an advisory lock (or a findOrCreate), key the lock on the *actual conflict columns* — the exact columns of the unique index you're protecting — not a coarser parent id. A lock keyed on a parent (`computeTargetId` alone) needlessly serializes every unrelated child (all `distributionId`s) in concurrent batches; key it on the composite `(distributionId, computeTargetId)` so only true conflicts block. AND when per-record locks are taken inside a loop, acquire them in a canonical order (e.g. sort the batch by the lock key) so two concurrent batches sharing keys can't grab them in opposite orders and deadlock. ## Analysis Mode (no PR context)
Find database structural-correctness issues. Use `rg` (respects `.gitignore`). Primary surfaces: `prisma/schema.prisma` (or `**/schema.prisma`), `prisma/migrations/**`, `apps/api`, `packages/api`, `packages/db` (if present). First locate the schema: `rg --files -g '*.prisma'`.

1. **Missing indexes on filtered/joined columns** — read `schema.prisma`, then for each model find columns used in `where`/`orderBy`/`join` without a matching `@@index`/`@unique`/`@id`. Cross-check usage: `rg -n "where: ?\{[^}]*\b<col>\b" apps/api packages/api -g '*.ts'`. Flag foreign-key scalar columns (e.g. `orgId`, `projectId`, `userId`, `sessionId`) that are filtered frequently but unindexed — these full-scan as the table grows. Remediation: add `@@index([orgId])` (or a composite matching the common `where`+`orderBy`). Pay special attention to `createdById` columns on Artifact and other filtered-by-creator patterns — the insights "My" scope queries filter on `(organizationId, createdById)`.
2. **Constraints enforced only in app code** — uniqueness/required relationships checked with a `findFirst` guard in TS instead of a DB `@unique`/`@@unique`/FK/`NOT NULL`. `rg -n "findFirst\(|findUnique\(" apps/api packages/api -g '*.ts'` near a subsequent `create` (check-then-insert race). Remediation: add the DB constraint + handle the unique-violation error, rather than a TOCTOU guard. Check tags/service.ts and deployments/deployment-service.ts specifically — they use findFirst→create with no unique constraint. Also check for dedup-by-{key} patterns inside READ COMMITTED transactions (phantom reads still produce duplicates). **CHECK-THEN-ACT SIBLING-PATH AUDIT (from PR #2720, 2026-07-13):** when you flag or fix one check-then-act race, sweep the same file for *sibling* paths that repeat the check-then-act on the same resource — self-heal/recovery/fallback branches (`resolvePromotion`-style "row exists but its child was removed, recreate it") are the ones that get missed and re-open the exact race the main fix closed. Fix them together, or the reviewer will bounce the PR.
3. **Unsafe migrations** — inspect the newest dirs under `prisma/migrations/`: destructive ops without a backfill/expand-contract (`DROP COLUMN`, `DROP TABLE`, `ALTER COLUMN ... NOT NULL` on an existing column with no default/backfill, type changes that truncate), `CREATE INDEX` (non-`CONCURRENTLY`) on a large/hot table (locks writes in Postgres), `CHECK` constraints added without `NOT VALID` (locks table scanning all rows), or renames done as drop+add (data loss). `rg -n "DROP |ALTER COLUMN|NOT NULL|CREATE INDEX|CREATE UNIQUE INDEX|CHECK" prisma/migrations -g '*.sql'`. **NEW-DEDUP-COLUMN-OVER-EXISTING-ROWS (from PR #2720, 2026-07-13):** when a migration adds a nullable "source"/"dedup" column PLUS a (partial) unique index over it and the app's new idempotency lookup keys on that column, pre-migration rows carry NULL and are invisible to the lookup — so the first retry after deploy re-creates the "duplicate" the feature exists to prevent. Flag the idempotency gap for existing data, but note the caveat: a naive backfill can *itself* violate the new unique index wherever historical duplicates already exist (the very rows the old bug created), so a safe backfill must parse the legacy source id out of prior content AND collapse per-key duplicates — a human data-migration/product decision, not something to auto-generate unattended. Recommend the human-owned backfill task; do not brick the migration by backfilling blind.
4. **Multi-write without a transaction** — two or more dependent writes (create + update, debit + credit, parent + children) issued as separate awaits with no `prisma.$transaction([...])` / interactive `$transaction(async tx => ...)`, so a mid-failure leaves partial state. `rg -n "await (db|prisma)\.[a-zA-Z]+\.(create|update|delete|upsert|createMany|updateMany|deleteMany)" apps/api packages/api -g '*.ts'` then read for adjacent dependent writes outside a `$transaction`.
5. **Read-modify-write races** — `findUnique`/`findFirst` → mutate in JS → `update`, with no transaction or optimistic-concurrency guard (version column / `update where: { id, version }`). Counters incremented this way lose updates under concurrency. Remediation: atomic `update({ data: { n: { increment: 1 } } })` or a transaction with the right isolation. Check agent versioning and document versioning for manual `version + 1` instead of `{ increment: 1 }`. (comments/service.ts resolveThread and unresolveThread are now FIXED — verified 2026-07-12: both wrap the read-mutate-write in `withDb.tx` and call `lockCommentThreadRow` = parameterized `SELECT id ... FOR UPDATE` up front — do NOT re-flag them.)
6. **Cascade / referential-action gaps** — relations with no `onDelete` policy where the intent is clearly cascade or restrict, leaving orphaned rows or failing deletes. Check relation fields in `schema.prisma` for missing `onDelete:`/`onUpdate:`. Pay special attention to Organization and User back-references from all owned-child models — they typically lack cascade and block org/user deletion. Also check junction tables for asymmetric cascade (one side cascades, the other does not). NEW-TABLE DELETE-PATH RECONCILIATION (confirmed 2026-07-09): when a NEW migration adds a table with an `onDelete: Restrict` FK to a HARD-DELETABLE parent (compute_target, artifact, session_detail, deployment), grep the parent's hard-delete service for a matching `tx.<newChild>.deleteMany({ where: { <parentFk> } })` — if the delete path predates the new table and doesn't remove the new child, the parent becomes undeletable (P2003 rolls back the whole tx). Real example: session_transcript (compute_target_id Restrict) broke computeTargetsService.deleteOwned. A `SetNull` FK on the same row to a DIFFERENT parent does NOT save it — the row survives and keeps the Restrict link. ORPHANED-OBJECT FOLLOW-THROUGH (confirmed 2026-07-10): when the child rows you clear carry an external object-storage pointer (e.g. `objectStorageKey` on session_transcript → raw JSONL in the transcripts S3 bucket), the `deleteMany` drops the only metadata linking those blobs, leaving them orphaned. Recommend collecting the keys (`findMany({ select: { objectStorageKey: true } })`) BEFORE the delete and then purging/tombstoning the objects in the same delete path — not the row deletion alone. Reviewers (Codex) will reject a delete-path fix that clears the rows but strands their objects. The object-lifecycle detail overlaps Storage Stefan — raise it once in this finding and reference him. FK-LESS MARKER/DEDUP TABLES + ALL-DELETE-PATH PARITY (confirmed good, PR #3084 2026-07-19): a table that records "we already handled X" (`pr_backfill_seen`-style seen/marker/dedup rows) often has NO FK to the entity it tracks, so no cascade reasoning and no `Restrict` failure will ever surface it — it simply survives the parent's deletion and silently suppresses the re-run after a legitimate delete-and-recreate. Detect these by name/shape (`*_seen`, `*_processed`, `idempotency_*`, dedup marker tables) rather than by relation, then enumerate EVERY path that removes the parent — manual/user-initiated delete AND the retention/expiry sweep AND any admin purge — and confirm they agree; a marker purged by `sweepExpiredSessions` but not by the manual delete is a real finding. Reviewers accepted this exact fix, so prefer "make the sibling delete path match the one that already purges" as the remediation.
7. **Over-fetch by default** — services returning full rows/relations via default `findMany` (no `select`/`include` discipline) where callers use a couple of fields, pulling large JSON/text columns needlessly. Flag the schema/service shape; pure result-set-size-at-scale belongs to Quinn — note the overlap.
8. **Enum / status drift** — a Prisma `enum` (or DB CHECK) whose members diverge from the TS union/string literals that write it, so the app can persist a value the DB rejects (or vice-versa). Compare the schema enum against the literals in `rg -n "status: ['\"]" apps/api packages/api`. Also check for string literals in comparison and assignment contexts where a shared const reference should be used instead (e.g., `"DRAFT"` instead of `DocumentStatus.DRAFT`).
9. **Raw SQL correctness** — `$queryRaw`/`$executeRaw` with string interpolation (`$queryRawUnsafe`, template `${}` of a variable into the SQL text). Flag from a correctness/parameterization angle (use `Prisma.sql`/parameterized `$queryRaw`); defer the injection-exploit writeup to Steve the Sec Engineer and reference him.
