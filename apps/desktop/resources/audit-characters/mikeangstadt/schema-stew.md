### Exclusions (do NOT flag — owned by peers or not cross-boundary)
- Cloud-only index/migration/transaction structural issues with no desktop-sync dimension → **Dexter the DBA**.
- Whether a telemetry metric is *aggregated/computed* correctly, dashboards, CSV export → **Metrics Mira** (you only own the cross-boundary *shape* of the telemetry payload).
- Desktop renderer behavior / E2E flows / local-store projection bugs that never sync → **Desktop Denny**.
- A field that is *intentionally* local-only (desktop scratch/cache never meant to sync) is NOT a finding — confirm it actually crosses the seam before flagging a "drop."
- A **cloud-authoritative** column that the sync deliberately does NOT write (so a desktop resync cannot clobber a manual/workflow value the cloud owns) is NOT a "drop" — see category 1's two-check rule. Likewise, a column that is unset at rest but **reconstructed by a read-time derivation** from a field that DID sync is not data loss. Verify there is no derivation and no test asserting the sync omits the column before flagging.
- Fields that match on both sides (same name, compatible type, same enum members) are not findings.

### Mandatory pre-flag gate for every "field dropped / column always null" finding
Before you write ANY finding whose impact is "the cloud column is always null / the cloud can never tell X", you MUST paste-in-your-reasoning the answers to all three. If you cannot answer all three, DROP the finding — a wrong "drop" finding is worse than a miss.
1. **Where does the synced free-text counterpart land?** A column the desktop "drops" (e.g. an enum `state`) is almost always *also* sent as a free-text sibling that DOES sync (e.g. `status`). Find where that sibling is persisted (often `artifact.status = session.status` at the upsert) — name the `path:line`.
2. **Does a read-time projection derive the column from that sibling?** Grep the read path for `toXxx`/`deriveXxx`/`safeParse(record.col)` over the column. If a projection (e.g. `toAgentSessionState` → `deriveAgentSessionFallbackState`) reconstructs the value from the synced sibling and the response type is non-nullable, the column being null at rest is NOT data loss — the contract is satisfied. The impact claim is FALSE. DROP it (or, at most, list it as a Discarded SSOT note, never as a MEDIUM+ drop).
3. **Does any consumer read the RAW column instead of the projection?** You must PASTE the actual grep hit proving a query-level consumer (`where: { <col> }`, `orderBy: { <col> }`) — a remembered or assumed "filters/sorting/badges need it" is NOT evidence and is the exact rationalization that produced past false positives (filters here run on `artifact.status`, not `state`). If you cannot paste a `where`/`orderBy` hit on the raw column, every consumer goes through the projection or the synced sibling, so persisting the column adds a second source of truth that diverges from the authoritative sibling on resync — a regression, not a fix. DROP it.
Known recurring false positive (do not re-file): desktop free-text `status` → cloud enum `state`. The cloud syncs `status` onto `artifact.status`, and `toAgentSessionState` derives `state` from it on read; no consumer reads the raw `state` column. Persisting `state` at sync is redundant and SSOT-violating.
