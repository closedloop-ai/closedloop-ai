### ⚠️ The published-package rule (READ FIRST — this is where you go wrong)
"No in-repo importer" does NOT mean dead. This monorepo publishes packages whose
exports are consumed OUTSIDE this repo — most notably `@closedloop-ai/loops-api`
and `@closedloop-ai/design-system`, which are built, published, and ingested by the
platform and external SDK consumers. An export with zero `rg` hits inside this repo
can still be load-bearing public API. Removing it breaks downstream consumers even
though CI here stays green.

So a symbol is a removal candidate ONLY if BOTH are true:
  (a) it has zero in-repo references (your usual check), AND
  (b) it is NOT part of any published package's public API surface.

### Step 0 — Build the public-API exclusion set BEFORE flagging anything
1. Enumerate every workspace `package.json`. A package is **published / public-surface**
   unless it has `"private": true`. Treat all non-private packages as published —
   explicitly including `@closedloop-ai/loops-api` and `@closedloop-ai/design-system`.
2. For each published package, read its `exports` map (plus `main`/`module`/`types`/
   `typesVersions`). Every declared entry point and subpath (e.g. `.`, `./attachment`,
   `./env-vars`, `./execution-result`, `./components/*`) is part of the public surface.
3. Resolve what each entry point exposes: every symbol exported (directly or
   re-exported, including `export *` barrels and type-only exports) from a file
   reachable through those entry points is PUBLIC. Add all of them to an exclusion set.
4. Any candidate in the exclusion set is OUT OF SCOPE — do not flag it, regardless of
   in-repo reference count. If you cannot cheaply prove a symbol is NOT reachable from a
   published entry point, treat it as public and skip it. When in doubt, do not cut.

### ⚠️ TOOLING gotcha: `\b` word-boundary anchors are UNRELIABLE under the rtk BSD-grep proxy (added 2026-07-11)
The rtk hook proxies `rg` to BSD grep AND masks the matched identifier token in printed line content (replaces the searched symbol with `ln`/`liy` in output). Two consequences: (1) NEVER trust masked line CONTENT from `rg` — use the Read tool (or `sed`/`grep -nE "^export"` with a non-symbol pattern) to read real names; `rg -l`/`-rln` FILENAMES are reliable. (2) A batch loop using `rg -l "\b$sym\b" ...` silently returns 0/garbage for symbols that are actually used (the `\b` anchors don't behave under the proxy), producing false "REFS=0" dead flags. VERIFY every candidate individually with a PLAIN (no `\b`) `/opt/homebrew/bin/rg -l "<NAME>" apps packages scripts .github` and eyeball that the sole matching file is the definition. This run a `\b`-anchored batch loop falsely flagged `ACTIVE_KIND_ALL` (actually used in 4 files) as REFS=0 — caught only by the plain-pattern re-check.

### ⚠️ TOOLING gotcha: `grep`/`rg` CONTENT vanishes when a big source file trips binary detection (added 2026-07-12)
The rtk proxy can leave stray NUL bytes in printed output, so `grep`/`rg` flags a large `.ts` file as "binary file matches" and SUPPRESSES all content lines — a 1724-line `service.ts` then appeared to have ZERO `export` keywords and looked like a dead exportless file. That is a false alarm, not a finding. Do NOT conclude "no exports / dead file" from an empty `grep -nE "^export"`. VERIFY file content with `awk '/^export/{print NR": "$0}' <file>` (awk is reliable under the proxy) or the Read tool before flagging anything about a file's export surface. This run `apps/api/app/agent-components/service.ts` falsely read as exportless; awk showed `export const agentComponentsService` at line 1295 (live, test-consumed) — no finding.

### ⚠️ TOOLING gotcha: binary-NUL suppression also HIDES cross-file importers — ALWAYS use `rg --text -l`; and `grep` may be aliased to `ugrep` which corrupts batch loops (added 2026-07-16)
Two compounding traps this run: (1) The same binary-NUL suppression that hides a file's exports ALSO hides it as an IMPORTER: a plain `/opt/homebrew/bin/rg -l "<sym>"` silently DROPS a large NUL-tainted consumer (e.g. `apps/desktop/src/main/database/write-core.ts` imports `numberFromUnknown`, but plain `rg -l` omitted it → false "ZERO refs / dead"). The `--text` re-check flipped `numberFromUnknown` (and could have flipped a filed finding) from false-dead to live. (2) In this runner `grep` is aliased to `ugrep`, which mangles `grep -oE "^export ..."` symbol extraction inside a for-loop so `$sym` becomes garbage and EVERY candidate falsely reports ZERO — a whole freshly-extracted helper dir (`apps/api/app/agent-sessions/service/*`) read as 100% dead. Prefer extracting names with `awk` (reliable) over `grep -oE`, and never file a batch-derived finding without a per-symbol `rg --text -l` re-check.

### SIGNATURE-ADJACENT TYPE exclusion: don't flag the param/return type of an exported function as an un-export (added 2026-07-14)
When an exported type is used ONLY as the parameter or return type of an EXPORTED function/hook in the same file (e.g. `PromoteInput`/`PromoteResult` for `promoteAgentComponent`, `RepoSource` for `fetchRepoComponents`, `ImportProgressDisplay` for `describeImportProgress`, `PackAnalyticsIpcDeps` for `registerPackAnalyticsIpc`, `UploadIntentRequest` for `useUploadIntent`), do NOT flag it as a dead/un-export candidate even at EXT=0. Callers legitimately need to name the argument/return type, so keeping it exported is intentional API symmetry and a reviewer will reject the un-export as style noise. This run I correctly skipped ~6 such signature-types and only flagged un-exports that are plain internal consts/components NOT part of any exported signature (`SESSION_STATUS_LABELS`, `TypeIcon`). Rule: an un-export finding is only worth filing when the symbol is a standalone internal const/helper/component with zero external importers AND is not the declared parameter/return type of an exported symbol.

### High-yield detection: DEAD `Object.values(...)` DERIVED-ARRAY ALLOWLIST EXPORTS (`*_IPC_CHANNELS`, `*_EVENTS`, `*_KEYS`) (added 2026-07-18)
A very common abandoned-convention dead-code family: a module defines a live const-object enum `<X>IpcChannel`/`<X>Events` (used for `ipcMain.handle` registration or a switch) AND right below it exports a DERIVED array `export const <NAME>_IPC_CHANNELS = Object.values(<X>IpcChannel)` intended for a preload channel-allowlist or a validation set that was never wired. The enum object+type stay LIVE, but the derived array is consumed nowhere — a lone occurrence at its own definition line. This run a per-module scan of `apps/desktop/src/main/ipc/*-ipc.ts` found 19 such dead `*_IPC_CHANNELS = Object.values(...)` arrays (agent-monitor, api-key, approvals, binary-paths, cloud-control, coaching, command-signing-keys, cost-reconciliation, debug, desktop-identity, jobs, logs-activity, managed-key-hint, onboarding, renderer-lifecycle, runtime-info, sandbox, settings, update) while a handful of siblings (PROFILE_CONFIG/DESKTOP_AUTH/DESKTOP_EXISTING_USER in tests, all SHARED_* in preload/contracts) were live. Detect mechanically: `/opt/homebrew/bin/rg --text -no "[A-Z_]*_IPC_CHANNELS" apps/desktop | sort | uniq -c` (or the `_EVENTS`/`_KEYS` analog) — any symbol whose repo-wide `rg --text -c "<NAME>" apps packages scripts .github` returns exactly ONE file (its definition) is dead. Remediation deletes ONLY the derived-array `export const ... = Object.values(...)` line, never the underlying enum object/type. File the whole family as ONE finding listing all `file:line` sites (shared root cause + remediation), like the tinted-Alert example in the shared brief. Safe because these are in `apps/desktop` (`"private": true`, no published `exports` map).

### ⚠️ TOOLING gotcha: golden-sessions data files flood `rg -l` as FALSE consumers (added 2026-07-21)
`packages/golden-sessions/**/raw/*.jsonl` + `normalized.json` are captured harness transcripts (frozen oracle data), NOT importers. They contain arbitrary session text that matches many symbol names verbatim (e.g. `getSharedAgentSessionUsage`, `DOCUMENT_TYPE_ICONS`, `STATUS_DISPLAY_ORDER` all showed 10-25 golden-session "hits" this run). A bare `/opt/homebrew/bin/rg --text -l "<NAME>"` then buries the 1-3 real code consumers under a wall of `golden-sessions/...jsonl` paths and can trick you into thinking a symbol is heavily used. ALWAYS pipe `| grep -v golden-sessions` (and ignore `apps/desktop/test/golden/layer2-snapshots/*.json`, same story) when ref-checking. A golden-session-only "consumer" set = ZERO real consumers = dead.
