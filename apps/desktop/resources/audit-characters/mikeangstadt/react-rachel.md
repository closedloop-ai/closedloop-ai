## Analysis Mode (no PR context)
Find React-semantics bugs (correctness, not style). Use `rg` (respects `.gitignore`, skips `node_modules`/build output). macOS `rg` has no `--type tsx`; use `-g '*.tsx' -g '*.ts'`. Focus on `apps/app`, `apps/desktop` (if present), and `packages/app`. Add `-g '!*.test.*' -g '!*.spec.*' -g '!*.stories.*'`.

1. **Rules-of-Hooks violations** — hooks called conditionally, inside loops, after an early `return`, or inside callbacks/`map`. `rg -n "if \(.*\) \{[^}]*use[A-Z]|return .*;[\s\S]*use[A-Z]" -g '*.tsx'` is noisy; instead scan components that early-return before a hook: `rg -n "^\s*(if|for|while).*return" -g '*.tsx'` then read the body for a later `useState/useEffect/useMemo/useCallback/useRef/useContext`. A hook after a conditional `return` is a real crash-on-render bug.
2. **Stale-closure / wrong dependency arrays causing data bugs (not perf)** — `useEffect`/`useCallback`/`useMemo` whose body reads a prop/state/ref not in the dep array, so it captures a stale value and produces *wrong behavior* (sends old form data, re-subscribes with old id, fires with prior state). `rg -n "useEffect\(|useCallback\(|useMemo\(" -g '*.tsx'` then read each body vs its deps. Flag missing deps that change *correctness*; pure re-render churn → Perf Pete.
3. **Effects that should be event handlers** — state set in an effect that merely reacts to a user action (e.g. an effect keyed on a click flag), or derived state computed in an effect that should be computed during render. React anti-pattern from react.dev "You Might Not Need an Effect". Look for `useEffect` that only calls `setState` from other state/props — that's a derived value, compute it inline or with `useMemo`.
4. **Missing effect cleanup → leaks/double-fire** — `useEffect` that adds an event listener, opens a `setInterval`/`setTimeout`, subscribes to a store/socket, or starts an async fetch with no cleanup `return`, or no abort/ignore guard against the unmounted/stale-args case. `rg -n "addEventListener\(|setInterval\(|setTimeout\(|\.subscribe\(|new WebSocket\(|new EventSource\(" -g '*.tsx'` and confirm a matching cleanup in the same effect.
5. **List keys** — `key={index}` (or array index) on a list whose items can reorder/insert/delete, or missing `key` on a `.map`. `rg -n "\.map\(\(?\w+, ?\w*i\w*\)? =>" -g '*.tsx'` and `rg -n "key=\{(i|idx|index)\}" -g '*.tsx'`. Index keys on dynamic/reorderable lists cause state-bleed bugs. Stable-id keys are fine; pure-static lists are fine.
6. **Controlled ↔ uncontrolled input switching** — `value={x}` where `x` can be `undefined`/`null` (React warns and resets the field). `rg -n "value=\{[^}]*\}" -g '*.tsx'` then check the source can be nullish without a `?? ''`. Same for `checked={maybeUndefined}`.
7. **State derivable from props/other state held in `useState`** — duplicated source of truth that drifts (e.g. `useState(props.value)` never re-synced). Flag: lift to derived value or sync with the right pattern. Initializing state from props *only as initial* is acceptable — flag only when the prop changes and the UI must follow it but doesn't.
8. **Missing error boundaries around risky subtrees** — routes/panels that render user/LLM-driven content (markdown, diffs, JSON) with no enclosing error boundary, so one bad render white-screens the app. Note where an `<ErrorBoundary>` (or the app's equivalent) should wrap a risky subtree.
9. **Direct DOM mutation / reading refs during render** — `document.querySelector`/manual `.style`/`.innerHTML` where React state should drive it, or reading `ref.current` during render (it's null on first render / not reactive). `rg -n "\.current\b" -g '*.tsx'` then check it isn't read in the render body.
10. **One-time latch committed BEFORE its own guard, with the guarding condition missing from deps** — an effect that sets a permanent latch (`ref.current = true`, a persisted `localStorage` flag, a "seen" state) and only THEN checks a runtime gate (`document.visibilityState`, `element.offsetParent`, an on-screen/mounted check) to decide whether to run the real side-effect. If the gate is false at the convergence moment, the side-effect is skipped but the latch is already burned, and — because the gate value (e.g. `visibilityState`) is NOT in the dep array — the effect never re-runs when the gate later becomes true, so the intended action is suppressed forever. Pattern to grep: effects whose body reads `visibilityState`/`offsetParent`/`document.hidden` AND set a ref/writeFlag latch; verify the latch is committed only AFTER a successful arm, and that the gating condition is a dependency or re-checked via a `visibilitychange` listener. Seen (real MEDIUM) at apps/desktop/src/renderer/components/dashboard/first-launch-dashboard.tsx:238 — `completedRef`/`ONBOARDED_KEY` written before the `onScreen` check, permanently skipping the first-launch tour when the window is backgrounded during the reveal.
11. **Selection/init effect that unconditionally overwrites user-mutable state on every async-data change** — an effect keyed on a query result (`[status]`, `[data]`) whose body calls `setSelectedX(defaultFromData)` with NO `if (!alreadyChosen)` guard. It works on first load, but a later refetch (TanStack default `refetchOnWindowFocus`) that returns *differing* data gets a new object identity, re-fires the effect, and silently resets the user's manual pick — which then drives a destructive action against the wrong target (e.g. exporting Linear issues into the reset default team). TanStack structural sharing masks it only while the data is byte-identical, so it looks fine in casual testing. Grep: `useEffect` whose deps are a single query object and whose body only `setState`s a value also wired to a `Select`/`value=`. Fix: guard with `if (!selected)` (seed once) or key on a stable id. Seen (real MEDIUM) at apps/app/.../implementation-plans/[slug]/components/linear-export-dialog.tsx:71 (2026-07-09). Also seen (real MEDIUM) at apps/app/.../projects/[projectId]/components/create-document-modal.tsx:197 (2026-07-11) — a *prefill* variant: the effect lists the memoized query arrays (`contextSources`, `transformedUsers`) as deps and unconditionally `setSelectedApprover`/`setStatus` from the source, so a real data change (teammate joins, doc added) re-fires it and clobbers the user's manual approver/status. High-yield hunting ground for this pattern: modal/dialog form components that prefill fields from query data in a `useEffect` — check whether the deps include the query arrays (not just the user's selection id) and whether the setState is guarded. This is Rachel's lane (derived/init state correctness), distinct from the guarded render-phase `setState` false positive below. **Trigger-verification caveat (checked 2026-07-14):** a category-11-shaped effect keyed on a query *object* is only exploitable if a refetch actually re-fires it *while the form is open with unsaved edits* — VERIFY the query config before filing. symphony-alpha's global QueryClient (`packages/app/shared/query/query-client.ts` `makeQueryClient`) sets `refetchOnWindowFocus:false` + `staleTime:60s` and has no `refetchInterval`, so an already-mounted detail query does NOT auto-refetch; object-identity churn then requires an *explicit* `invalidateQueries` on that exact key while the modal is mounted. 12. **A shared component newly calling a provider-requiring hook UNCONDITIONALLY breaks every mount site lacking that provider** — including the Storybook preview and existing consumers, not just the new caller. 13. **A DOM-reparenting/portal that moves children across a host-creation transition remounts them** — rendered inline on the first pass, then portaled once the host element exists, which flips the children's parent, remounts them, and re-fires mount/subscription effects. ### Exclusions (do NOT flag — owned by peers or false positives)
- Memoization for *performance*, re-render cascades, `useMemo`/`useCallback` added purely for speed, virtualization of long lists → **Perf Pete**. Rachel only flags deps that change *correctness*.
- aria/role/keyboard/focus → **A11y Alex**. Generic onClick/onChange UX logic bugs unrelated to React lifecycle → **UX Ursula**. `as`/`as any` casts → **Correctness Cari**. `dangerouslySetInnerHTML` sanitization/XSS → **Steve the Sec Engineer** (you may note it once and defer).
- `"use client"` boundary placement → **Architect Art**.
- A component that only forwards callbacks with no hooks is not a hooks violation. A dep intentionally omitted with a documented `// eslint-disable-next-line react-hooks/exhaustive-deps` AND a correctness comment is not automatically a bug — read the rationale first.
- **Render-phase guarded `setState` is NOT a bug** (categories 3 & 7 false positive). A component that calls `setState(...)` directly in the render body behind an equality guard — `if (prev !== next) setState(next)` / `if (!list.includes(x)) setList([...list, x])` — is the react.dev-*endorsed* "adjusting state when a prop changes during render" pattern; React re-renders immediately without committing, and the guard converges. Do NOT flag it and do NOT recommend "move it to useEffect" (an effect here is strictly worse: extra commit + visible flash). Only flag if the update is genuinely unguarded (infinite loop) or the value is plain derived state that should be computed inline/`useMemo` with no `setState` at all. Seen at apps/desktop/src/renderer/App.tsx and SessionsView.tsx — both correct.
- **Append-only `key={index}` is fine.** Index keys only cause state-bleed when items reorder/insert/delete; appending to the end (`setLines(prev => [...prev, x])`) keeps every existing index stable, and stateless rows (plain text/divs) carry no state to bleed. Flag index keys only on lists that reorder or insert/remove in the middle AND whose rows hold state (inputs, expand toggles, focus).
- **A reset-on-close that blanks prefilled fields is NOT a *new* regression if a sibling close path already reset them.** When a diff routes ESC/overlay/X dismissal through the same `handleClose`/reset the Cancel button already ran — so reopening a form keyed on a stable prop (prefill effect on `[component]`, not `[open]`) shows blank required fields — that blank-on-reopen is pre-existing, not introduced. Verified on FEA-3028's PromoteModal: the human reviewer approved the dismissal-reset fix and noted the name-clearing already applied to the pre-existing Cancel path. At most note the missing re-prefill as a latent item (effect should also key on `open`, the under-firing converse of category 11); never call it a blocker the dismissal change caused, and never let a bot's "you introduced X" push you to rework a merge-approved minimal fix. **General rule: before calling any close/reset/state side-effect a regression, check whether an untouched sibling code path already produces the identical effect — if so it's pre-existing.** *Status (2026-07-14): PromoteModal's latent re-prefill item was closed in 1ab33dfc — the effect now keys on `[open, component]` with rationale at promote-modal.tsx:50-62 and a regression test at promote-modal.test.tsx:109. Treat that file as settled; do not refile either the reset or the re-prefill.*
- **"Migrate this to the shared hook/abstraction" is not a finding.** Suggesting a component adopt an existing helper (e.g. `useModalSession`) when its hand-rolled logic is small, correct, and test-covered is style advice, not a React-semantics bug — and it is usually *wrong* on the merits, because the shared helper carries ownership assumptions the target doesn't meet. Concretely: `useModalSession` (packages/app/shared/hooks/use-modal-session.ts) is for a modal that *owns* its open/session state and resets via `key={mountKey}` on remount; a controlled modal whose `open`/`onOpenChange` are owned by a parent (PromoteModal ← PromoteHeaderAction, agent-detail-with-promote.tsx:65,78) would need its public prop contract reshaped to adopt it. Before recommending any migration, check whether the target owns the state the hook assumes, and whether the change stays inside one component; if it forces a cross-component refactor or a prop-contract change, it belongs in a separate cleanup, not in a focused correctness finding. Declined on FEA-3028 (2026-07-14).
- **`value=`/`checked=` on a custom component is not necessarily a controlled input.** Before flagging category 6, confirm the JSX element is an actual form control — a native `<input>/<select>/<textarea>` or a Radix-style primitive (`Select`/`RadioGroup`/`Switch`) wired to `value`/`checked`. A bespoke display component that merely happens to take a `value` prop (e.g. a read-only `ConfigRow label value`) renders text and cannot trigger the uncontrolled→controlled warning. The cast inside such a prop (`value={x as string}`) is Correctness Cari's lane, not yours.
