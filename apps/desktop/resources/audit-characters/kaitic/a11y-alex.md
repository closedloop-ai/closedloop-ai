**When fixing an icon-only control, READ where it renders first — do NOT blindly wrap it in a `<button>`:**
- If the icon sits inside an element rendered via a Radix `asChild` trigger (`PopoverTrigger`/`DropdownMenuTrigger`/`TooltipTrigger asChild` over a `<Button>`) or otherwise already inside a `<button>`, wrapping the icon in a real `<button>` produces **invalid nested-button DOM** (hydration error, browser reparents it, layout breaks). Instead make the existing icon focusable: `role="button"`, `tabIndex={0}`, `aria-label`, and an Enter/Space `onKeyDown` handler. (Real case: the clear `<XIcon>` inside `date-picker-popover.tsx`'s combobox trigger.)
- The design-system `<Button>` base CVA class applies `[&_svg]:pointer-events-none` to **all** SVG children. So an `onClick`/`hover:` on an `<XIcon>`/lucide SVG inside (or asChild-merged onto) a Button is **dead for mouse** — the click falls through to the parent. If you add or keep a click/keyboard handler on such an SVG, also add `pointer-events-auto` (and usually `cursor-pointer`) to its className, or move the handler onto a non-SVG wrapper element. A keyboard `onKeyDown` works regardless of `pointer-events`, so verify the MOUSE path too, not just the keyboard one.
- A handler on a control nested in an outer trigger must `e.stopPropagation()` (and `e.preventDefault()` for keyboard) so it doesn't also fire the outer trigger (e.g. open the popover while trying to clear).
- **Never ADD `role="button"` (or a card-level keyboard handler) to a clickable CONTAINER that renders interactive children** — buttons, links, menus, file chips, inputs. This is the same nested-interactive anti-pattern the Analysis Mode rule forbids, and it bites just as hard in Fix Mode. Concrete regression: the 06-20 sweep added `role={onClick ? "button" : undefined}` to design-system `CommentThreadCard`, whose `pr-comment-card.tsx` caller passes `interactive`/`onClick` while rendering a nested `PrCommentActionMenu` (Edit/Delete/Resolve). Result: (a) the card's accessible name collapsed to its whole subtree, so `getByRole("button", { name: /Edit/ })` matched both the card and the Edit button and `branch-pr-comments-section` tests failed with "multiple elements found", and (b) it created an invalid button-inside-button a11y tree. A generic shared primitive consumed by callers that pass `onClick` for a mouse surface is NOT where role/keyboard belongs — the caller already supplies (or should supply) a dedicated `sr-only` keyboard affordance. Leave the container as a plain clickable `<div>` (keep its existing `tabIndex`/`onKeyDown` if present) and do not add `role="button"`. Only a container that is the SOLE interactive element with no nested controls may take `role="button"`, and then gate activation on `event.target === event.currentTarget`.
- **cmdk `<CommandInput>` labels go on the `<Command>` root, not the input.** Adding `aria-label` to `<CommandInput>` is a no-op: cmdk overrides it with an auto-generated `aria-labelledby`. Fix it as `<Command label="Search …">` (the design-system `Command` forwards `label` to cmdk's hidden label element) and drop any `aria-label` you put on the input. Verify with typecheck — `label` is a valid prop on the `Command` root.
