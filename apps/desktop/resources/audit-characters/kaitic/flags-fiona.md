### New detection pattern (2026-07-07): multi-flag one-flow coordination hazard
When ONE end-to-end flow spans surfaces (desktop → web, or client → server) and each surface has its OWN flag with no shared source or lockstep, enabling only one half silently strands the user (dead-end page, no-op action). This is distinct from a raw-literal drift (values may differ by design) — the defect is the MISSING coordination/ordering, not a typo. Detect: for any cross-surface feature, list every flag its stages read; if a stage-1 gate (UI entry) can be on while a stage-2 gate (the page/endpoint it hands off to) is off, and stage-2's off-path is a dead-end rather than a graceful fallback, flag it MEDIUM. Remediation: have the entry stage resolve the downstream flag (or a server availability check) before proceeding, or document/enforce a rollout order (downstream flag to 100% before the entry flag ships enabled). Also check gate PLACEMENT: a dark-launch flag enforced only in the renderer (hiding a tab) while the main-process/server capability (IPC handler, route) is registered unconditionally means toggling the flag off does NOT disable the capability — flag as FLAG_GATE_UI_ONLY (defer security/exploit angle to Steve). When the remediation is a user-facing WARNING / prerequisite note on a desktop flag, it must land on the ACTUAL toggle the operator flips — the hand-rolled `LAB_FLAGS` entry in `SettingsPanel.tsx` that renders the Labs toggle copy — NOT only the shared `FEATURE_FLAGS` registry, which does not drive that toggle's label/description (see the DUPLICATE_FLAG_CATALOG drift below). A lockstep warning added to the registry alone never reaches the operator enabling the flag (PR #2353).

### New detection pattern (2026-07-08): registry SSOT vs hand-rolled parallel flag catalog
A flag REGISTRY (a single array/object that is documented as the source of truth and drives the settings/admin UI + get/set accessors) can be silently bypassed by a SECOND hand-maintained list that re-declares the same flags' metadata (label/description/category/requiresRestart) for rendering. The two drift: metadata diverges and newly-registered flags never appear in the UI. Detect: after finding a registry (e.g. desktop `FEATURE_FLAGS`), grep the settings/renderer for a second literal array of flag entries (`rg -n 'label:.*description:|category:.*requiresRestart|key:.*label:' apps/desktop/src/renderer`), and compare its keys+metadata against the registry. Any key present in one but not the other, or a `requiresRestart`/`category`/`label` mismatch, is DUPLICATE_FLAG_CATALOG (MEDIUM). Remediation: drive the UI from the registry (often already exposed over IPC, e.g. `get-all-flags` returns `registry`) and delete the parallel list. Distinct from raw-literal drift — here the drift is in flag METADATA/catalog membership, not a key string.
