### When writing fixes
- **Preserve visual fidelity when mapping to semantic variants.** A hand-rolled style
  (e.g. `bg-red-50 text-red-700` subtle outline) is NOT equivalent to a semantic variant
  that renders differently (e.g. `variant="destructive"` = solid red fill). Check the
  variant's actual rendered weight/fill/color before swapping; a subtle status chip must
  not become a loud error fill.
- **TEXT gets the `-foreground` token; the bare accent token is for FILLS and BORDERS.** This is
  the single most-rejected mistake in fix PRs (4 separate reviewer comments on the night of
  2026-07-20 alone: FEA-3020, FEA-2901, FEA-2902, FEA-2635). Swapping a hardcoded
  `text-orange-700`/`text-blue-600`/`text-emerald-600` to `text-warning`/`text-info`/`text-success`
  looks like the right semantic move but is a **contrast regression**: the bare `--warning`/`--info`/
  `--success` tokens are high-lightness *accents* (~3.1–3.4:1 on `--card`), below the 4.5:1 AA
  threshold the raw scale used to clear. The paired `--*-foreground` tokens are the darker readable
  text values. So: `bg-warning/10` for the chip, `text-warning-foreground` for the label AND the
  icon inside it. The authority is the shared status color map in
  `packages/app/shared/components/status-badge.tsx` — `COLOR_PENDING`, `COLOR_PROGRESS`,
  `COLOR_SUCCESS`, `COLOR_AI` are all `bg-X/10 text-X-foreground border-X/30`. Copy that triplet
  verbatim rather than composing tokens by hand.
  - **The one documented exception is `destructive`.** `--destructive-foreground` is `oklch(1 0 0)`
    (white — meant for text on a *filled* destructive background), so it is invisible on a card.
    `COLOR_FAILURE` is deliberately `bg-destructive/10 text-destructive` — error text sits on the
    accent by design. When a reviewer flags destructive-text contrast, do NOT revert to raw
    `red-600` (that diverges from the convention) and do NOT reach for `-foreground`: hold the line
    on `text-destructive`, and say plainly that the residual contrast is a design-system *token
    value* question to fix globally on `--destructive`, not to special-case per tile. This reply was
    accepted on both PR #3128 and PR #3130.
- **Banner→`<Alert>` swaps are NOT mechanical className edits — verify per-instance, in this repo specifically.** The `alert.tsx` `cva` here is the *opposite* of the generic warning above: `variant="destructive"` renders `text-destructive bg-card` — **red text on a plain card background, NO fill**. So swapping a *tinted* error banner (`bg-destructive/10 border-destructive/30`) to `<Alert variant="destructive">` **removes** the tint — a regression. Beyond color, hand-rolled banners also differ from `<Alert>` in **geometry and DOM**: `rounded-md` vs Alert's `rounded-lg`, `p-3` vs `px-4 py-3`, `bg-*/12` vs `bg-*/10`, and Alert is a CSS *grid* with icon/title/description slots — wrapping a one-line `<div>` banner restructures the markup. Read the exact `cva` string for each target variant and compare fill, radius, padding, and structure against the hand-rolled source; a bulk banner-consolidation sweep (e.g. "replace these 29 banners") is **needs-human-visual-review / Storybook**, NOT something to apply mechanically overnight. The genuinely safe, auto-applyable slice is *additive*: adding new `cva` variants (e.g. `info`/`success`, only after confirming the `--info`/`--success` tokens exist) — split that from the risky replacements.
- **Match the SIZE token to the actual dimensions, not a guess.** Read the component's
  `cva` size map and pick the size whose `h-`/`px-` values equal the hand-rolled ones.
  Real miss: a hand-rolled `<Link>` styled `inline-flex h-9 ... px-4` was recommended as
  `<Button size="sm">`, but in this repo `size="sm"` = `h-8 px-3` and `size="default"` =
  `h-9 px-4` — `sm` would have shrunk the control. When dimensions equal the default size,
  omit `size` entirely. Note the variant's color tokens may have drifted from the
  hand-rolled copy (e.g. `outline` = `bg-input hover:bg-muted`, not the stale
  `bg-background hover:bg-accent`); swapping to the live variant to re-converge is the
  intended outcome — call that out, don't silently treat it as pixel-identical.
- **Keep sibling elements visually consistent.** Don't leave a set of related badges/chips
  using mixed weights (one solid-fill, one subtle-outline, one hand-rolled). If no semantic
  token matches the intended look, keep the whole hand-rolled set rather than converting
  only some members.
- **NEVER assert "there is no semantic token for this color" without grepping the token list
  and the shared color map first — and never bake that claim into a code comment.** Burned on
  FEA-3020 (2026-07-20): a chip was left on a raw purple scale with a committed comment reading
  "purple has no design-system semantic token", which was flat wrong — `--ai` / `bg-ai` /
  `text-ai-foreground` exists, and `LoopEventType.ToolCall` was *already* mapped to `COLOR_AI` in
  `status-badge.tsx`. The hand-rolled purple was drifting from the very map that governs that event
  type. Before concluding a token is missing: grep `packages/design-system/styles/globals.css` for
  the `--*` custom properties, and grep the `COLOR_*` constants in
  `packages/app/shared/components/status-badge.tsx` for the entity/status you are styling — the map
  may already assign one. Beyond `destructive`/`warning`/`info`/`success` the palette includes `ai`.
  A justification comment that names a token gap is a claim reviewers WILL check; if you cannot cite
  the grep that proves the gap, leave the code alone and say nothing rather than committing a
  false premise.
