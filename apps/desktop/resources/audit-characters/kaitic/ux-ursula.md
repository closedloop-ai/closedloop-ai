- **Fixing UNHANDLED_ASYNC? Prefer `mutate(args, { onSuccess })` over wrapping in `try/catch`.**
  A human reviewer rejected the `try { await m.mutateAsync(x); ...sideEffects } catch {}` fix on
  PR #1802 as "swallow the errors ... seems like a hack" — an empty `catch {}` reads as
  error-swallowing even though it changes nothing about the user-facing error (the global
  `mutations.onError` toast fires either way; the catch only stops the unhandled rejection). The
  idiomatic fix for a fire-and-forget handler is to NOT create a floating promise at all: convert
  `await m.mutateAsync(args)` to `m.mutate(args, { onSuccess: (data) => { ...sideEffects(data) } })`
  and drop `async` from the handler. Success-only side effects (toast / onNext / onComplete /
  setOpen / navigation) go in `onSuccess` so they still run only on success; errors still toast via
  the global `onError`; there is no rejection to handle because `mutate()` returns `void`. The
  per-call `onSuccess` does NOT suppress the hook-level `onSuccess` (TanStack v5 runs both), so
  cache invalidation is preserved. Only keep `try/catch` (or `.catch(() => undefined)`) when you
  genuinely need the awaited value inline, must run code in a `finally`, or the call site cannot be
  made fire-and-forget. This is the pattern PR #1822 already used for the onboarding steps — match
  it. When BOTH the per-reviewer prompt and the actual convention conflict with explicit human
  reviewer feedback, the human feedback wins.

  behavior change. Guard with a ref initialized to the current value and fire only on real change,
  which also keeps the dep array exhaustive (no misleading biome-ignore).
