## Analysis Mode (no PR context)

The tool registration table and per-session wiring live in `apps/mcp/src/index.ts` (`TOOL_REGISTRATIONS`, `createMcpServer`, `handleMcp`); shared helpers in `apps/mcp/src/tools/tool-utils.ts` (`withErrorHandling`, `encodePathSegment`, `buildPaginatedPayload`, `describeIdOrSlug`); the upstream client in `apps/mcp/src/api-client.ts`.

1. **Tool input schema that under-validates or drifts from the handler.** A Zod field typed looser than the handler/API needs, so the LLM sends a value the server then mangles or the upstream rejects. Read each tool's `inputSchema` against its handler: `rg -n "z\.string\(\)|z\.number\(\)|z\.enum\(|\.optional\(\)|\.uuid\(\)|\.url\(\)" apps/mcp/src/tools`. Concrete tells in this repo: `complete-loop` (`apps/mcp/src/tools/complete-loop.ts`) types `prUrl` as bare `z.string()` though its description calls it "the pull request URL" — no `.url()`; `create-loop` (`apps/mcp/src/tools/create-loop.ts`) marks `repoFullName`/`repoBranch` `.optional()` and the handler only sends `repo` when BOTH are present (`if (repoFullName && repoBranch)`), so passing exactly one is silently dropped with no validation error. Remediation: tighten the Zod type (`.url()`, `.uuid()`, `.min(1)`, `z.enum(...)`) to match what the handler/API actually requires. For co-dependent params like `create-loop`'s `repoFullName`/`repoBranch`, enforce the both-or-neither rule in the HANDLER body (throw a validation error) — do NOT hand `registerTool` a `.refine()`d `z.object()`: `inputSchema` must stay a plain `ZodRawShape` field-map (the SDK builds the object itself, so a passed `ZodObject`/`ZodEffects` is rejected/mistyped). NEW detection tell (verified 2026-07-10, FEA-2536 slice): **a tool param typed `.optional()` while the upstream API validator REQUIRES it.** The MCP `create-document` tool marks `projectId` `.optional()`, but `apps/api/app/documents/validators.ts` `createDocumentValidator` has `projectId: uuidOrSlug()` (required, `.strict()` schema) — so an LLM that trusts the optional schema and omits it is guaranteed a server 400. Detection: for every `.optional()` tool param that maps to an upstream write body, open the matching `apps/api/app/*/validators.ts` schema and confirm the field is ALSO optional there; a required-upstream field must be required in the tool. DESCRIBE THAT FAILURE MODE ACCURATELY in the fix and any test comment: a `.strict()` validator rejects a MISSING field with a **400 before the resolve step (`resolveProjectId`) ever runs**; a `notFoundResponse("Project")` (404) applies ONLY to the separate case where the field IS supplied but doesn't resolve to a row. Do NOT conflate the two — claiming the omitted-field case returns `notFoundResponse`/404 is a MEDIUM documentation nit reviewers WILL flag (verified 2026-07-11, FEA-2886 fix PR #2553). Do NOT flag the reverse (tool required / API optional) — that's safe. `rg -n "createDocumentValidator|updateDocumentValidator" apps/api/app/documents/validators.ts` and compare field-by-field to the tool's `inputSchema`.
2. **Tool/param description that is inaccurate or misleading.** The LLM picks and fills tools purely from these strings — a wrong one is a silent mis-call generator. Compare every `description:` against what the handler does: `rg -n "description:" apps/mcp/src/tools`. Tell: `create-loop`'s description says "Always include repoFullName and repoBranch" while the schema marks them optional and the handler drops a lone one (see #1) — the description over-promises a guarantee the schema/handler don't enforce. Remediation: rewrite the description to state exactly what the handler accepts/returns; if it documents a field/route the handler no longer touches, delete the claim.
3. **Tool output shape not matching what the tool promises.** Tools have NO `outputSchema` (`rg -n "outputSchema" apps/mcp/src` returns nothing) — every result is `content: [{ type: "text", text: JSON.stringify(...) }]`, sometimes the raw upstream payload (`get-project`), sometimes a hand-shaped projection (`list-loops`, `update-document` add a `webUrl`; `create-branch-artifact` reduces to `{ id }`; `get-document-comments` re-keys `author: c.authorId`). The bug: a description promises a field the shaper drops, or the shaper assumes a row shape (`asRecord`/`readString` over upstream JSON) that has since changed. Read each shaper against the fields its description names: `rg -n "JSON.stringify|mapItem|shape|asRecord\(" apps/mcp/src/tools`. Remediation: align the projection with the documented fields (or add a real `outputSchema`/`structuredContent` so clients can rely on it), and ensure `buildPaginatedPayload` consumers actually receive the array shape `extractArrayItems` expects.
4. **Transport / streaming correctness.** The `/mcp` handler (`handleMcp`, `handleMcpExistingSession`, `handleMcpStatelessRequest` in `index.ts`) runs streamable-HTTP with a stateful `mcpSessions` map AND a stateless fallback for unknown session ids behind non-sticky load balancers. Check: a stateful session created on POST stores `{ server, transport }` but the stateless fallback `createMcpServer` → `server.connect(transport)` → `server.close()` per request — verify a request mis-routed between the two paths can't leak a transport, double-handle a body, or `handleRequest` twice. `rg -n "handleRequest|sessionIdGenerator|server.close|mcpSessions" apps/mcp/src/index.ts`. Tell to verify: GET/DELETE on an unknown session id 404s while POST falls through to stateless — confirm that branch matches the SDK's session-resumption expectations. Remediation: make the routing branch explicit per HTTP method and ensure every created `McpServer`/transport is closed exactly once.
5. **Capability negotiation & protocol-version handling.** `SUPPORTED_PROTOCOL_VERSIONS = ["2024-11-05", "2025-03-26"]` (`index.ts`) is advertised in the `/.well-known/mcp.json` server card and `capabilities: { tools: true }`, but grep shows it is NOT passed into the `McpServer` constructor or transport — negotiation is left entirely to the SDK default. Verify the advertised versions/capabilities actually match what the running server negotiates and what it implements (the card claims only `tools`, yet `instructions` are passed to `McpServer` — confirm no resources/prompts capability is implied but unbacked). `rg -n "SUPPORTED_PROTOCOL_VERSIONS|capabilities|protocol_version|new McpServer" apps/mcp/src/index.ts`. Remediation: make the advertised card a single source of truth derived from what the server actually registers, or stop advertising a version/capability the server doesn't honor.
6. **Missing or coarse authorization on tools.** Tool exposure is gated only at *registration* time in `createMcpServer`: `requiresWrite` hides write tools unless `hasWriteScope(grantedScopes)`, and `requiredScopes` (only `delete-attachment` uses `["delete"]`) hide others — there is NO per-call authz inside any handler. Audit `TOOL_REGISTRATIONS` (`index.ts`) for a mutating tool missing `requiresWrite`, or a destructive tool (delete/cancel/fail) not behind a `requiredScopes` gate: `rg -n "requiresWrite|requiredScopes|registerTool" apps/mcp/src/index.ts apps/mcp/src/tools`. Tell to verify: every `apiClient.post/put/delete` tool should carry `requiresWrite: true` (or a tighter scope) in the table — a write handler registered without it is callable by a read-only key. Remediation: add the missing `requiresWrite`/`requiredScopes` entry; defer OAuth-flow/crypto exploits to Steve.
7. **Malformed or leaky error responses.** Tool errors flow through `withErrorHandling` → `formatToolError` (`tool-utils.ts`), which returns `{ isError: true, content: [text] }` and appends `Technical details:` `JSON.stringify(friendly.technicalDetails)` plus the upstream `McpApiError` `details`/`status` (`api-error.ts`, `api-client.ts` `getResponseError`/`unwrapApiResult`). Remediation: redact internal fields from `technicalDetails`, and ensure handlers never throw outside `withErrorHandling`.
8. **Non-idempotent tools without a guard.** A tool whose handler issues multiple dependent upstream writes can leave partial state when re-invoked (the LLM retries freely). Tell: `complete-loop` posts a `completed` manual-event THEN does a separate metadata `apiClient` update (`apps/mcp/src/tools/complete-loop.ts`) — a re-call double-emits the event; `create-loop`/`create-project`/`create-document` have no client-supplied idempotency key. `rg -n "apiClient\.(post|put|delete)" apps/mcp/src/tools` and read for two writes in one handler or a create with no natural idempotency. 9. **Resource URI / path-segment handling.** User-supplied ids (slugs like `FEA-42`, UUIDs) are interpolated into upstream URL paths; `encodePathSegment` (`encodeURIComponent`, `tool-utils.ts`) is the path-traversal guard.
